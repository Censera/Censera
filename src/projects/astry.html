Astry

Astry is a statically typed compiled language designed for game development. Its v26 design uses explicit syntax for types, pointers, casts, and logical versus bitwise operators. The compiler is written in Rust and uses ani as its LLVM interface.

Implementation status: Astry's specification describes more language behavior than the current compiler implements. The CLI reaches the semantic stage and then returns StageNotImplemented(Semantic). End-to-end code generation is not available yet.

Source of truth

doc/syntax.md is the source of truth for v26 spelling and grammar. It also lists open questions marked Q1 through Q20; those behaviors are not settled. The other design documents explain the purpose, architecture, and planned work, but do not override the syntax specification.

Project boundaries

The intended pipeline is:

source
    -> lexer
    -> return-type normalization
    -> macro expansion
    -> declaration index
    -> parser / AST
    -> semantic analysis
    -> LLVM IR
    -> native output

The early token and parser stages have implementation and tests. Semantic analysis and native output are not complete. See Status and roadmap before relying on a feature described by the specification.

Quick start

This page covers the repository's current development workflow. It does not imply that Astry can already compile a complete program to native output.

Requirements

  • Rust and Cargo with support for the crate's Rust 2024 edition.
  • The LLVM/toolchain setup required by ani version 26.
  • Git.

The repository's .cargo/config.toml sets LLVM_SYS_no_polly = "1" and LLVM_SYS_no_ffi_libs = "1". Consult ani and the installed LLVM package for the remaining build requirements.

Get the source

git clone https://github.com/Censera/astry.git
cd astry

The default branch reported by the repository is entry.

Build and test the Rust project

cargo build
cargo test

These commands build and test the compiler implementation. They do not demonstrate end-to-end native compilation of an Astry program.

Current CLI

The current command-line entry point accepts a single source-file path:

cargo run -- path/to/main.astry

For example, the language specification uses function declarations such as:

fn i32 add(a i32, b i32) {
      return a + b
  }

  fn i32 main() {
      return add(20, 22)
  }

At this stage, a syntactically valid program reaches the semantic stage and the compiler returns an error equivalent to:

compiler stage is not implemented: Semantic

The CLI does not yet expose output-path, target, optimization, check-only, or IR-emission options. Those are tracked in todo/entry.md.

  • src/parser/: declarations, expressions, and AST construction.
  • src/semantic/: semantic-analysis data structures and type syntax.
  • src/backend/: the LLVM wrapper layer.
  • src/utility/compiler.rs: compiler entry points and stage orchestration.
  • doc/syntax.md: authoritative language syntax.

Language overview

This page summarizes the v26 language design. It is a guide to the specification, not a promise that every listed feature is implemented in the compiler.

A small example

fn i32 clamp(value i32, low i32, high i32) {
    if value < low {
        return low
    } elif value > high {
        return high
    } else {
        return value
    }
}

fn i32 main() {
    let value = clamp(12, 0, 10);
    return value
}

Function return types appear before the function name. Parameters use name type; a binding may infer its type or declare it explicitly. The semicolon on a block's final expression matters: an expression without ; can be the block's value.

Bindings

let declares a reassignable binding. const declares a binding that cannot be assigned again. A type annotation follows the name.

let count = 0;
let ratio f64 = 0.5;
const LIMIT u32 = 100;

count = count + 1;

Shadowing is allowed: a later declaration can hide an earlier binding in its scope. It creates a new binding rather than modifying the old one.

Functions and calls

fn i32 add(a i32, b i32) {
    return a + b
}

let result = add(20, 22);

Functions can be overloaded. The design allows overloads to differ by parameter types/count or return type; when overloads differ only by return type, the expected type must disambiguate them.

The @Stripped flag permits calls without parentheses, and @Loosely marks a parameter list containing .... These forms have unusual argument-boundary rules. See doc/syntax.md before using them.

Blocks and control flow

The specification includes if, elif, else, loop, while, for, break, continue, and match.

for i in 0..10 {
    if i == 5 { break }
}

.. is a half-open range and ..= is a closed range. Loops may have labels; a labeled break or continue targets that loop.

A block can produce a value when its last item is an expression without a trailing semicolon:

let sum = {
    let a = 20;
    let b = 22;
    a + b
}

Some block and control-flow details remain open in the syntax document, including what a conditional expression without else yields.

Types

The v26 type list includes:

Syntax Meaning in the specification
i8 through i64Signed integers
u8 through u64Unsigned integers
f32, f64Floating-point values
bool, char, stringBoolean, character, and string values
^TNon-null pointer to T

T[n]Fixed-length array

Union<A, B>Value holding one member type
Named typesStructs, enums, and aliases declared by the program

The default type for unsuffixed numeric literals is unresolved. Memory ownership for strings and vectors is also unresolved.

Pointers and casts

The design makes pointer operations explicit:

let value i32 = 5;
let pointer ^i32 = &value;
let copy i32 = pointer^;
let widened ?^i32 = pointer;

&value takes an address, postfix ^ dereferences a pointer, and -> performs an explicit cast:

let digit = 1 -> char;

The distinction between ^T and ?^T is checked in semantic analysis. Lifetime behavior and some optional-pointer conversions remain open questions.

Operators

Logical operators use &&, ||, ~~, and !, with keyword alternatives and, or, xor, and not. Bitwise operators use a separate family: :&, :|, :^, :<, :>, and <:. The specification rejects plain & as a bitwise operator.

The syntax document still lists operator precedence and some increment/decrement details as open questions. Parenthesize ambiguous expressions until the rules are settled.

More language constructs

The syntax specification also describes modules and imports, structs, enums, into blocks, user-defined types, unions, macros, embedded C, and experimental lambdas. Several construction, dispatch, type, and lifetime rules remain unresolved. See Syntax reference and the authoritative doc/syntax.md.

Syntax reference

This page collects the rules most likely to affect everyday reading. The complete and authoritative reference is doc/syntax.md, including examples, compiler notes, and open questions Q1 through Q20.

Tokens and terminators

  • Most statements end with ;.
  • mod and use lines do not take a semicolon.
  • A final expression in a block may omit ;; that determines whether the block yields a value.
  • 'x' is a character literal. A form such as 'outer is a loop label.
  • ^ is used for pointer types and postfix dereference; & is prefix address-of.
  • -> is an explicit cast.
  • .. and ..= form half-open and closed ranges.

The keyword set in v26 is: mod use let const fn return if elif else loop while for in break continue match enum struct type into pub pri embed macro and or xor not true false None.

Declarations

mod game
use { standard, math }

let score i32 = 0
const MAX_SCORE i32 = 100

fn i32 add(a i32, b i32) {
    return a + b
}

The type follows a binding name and a function's return type precedes its name. Explicit types are optional for bindings but are part of the function form described in the syntax specification.

Visibility markers are pub and pri. The default visibility has not been decided in the specification.

Block values

A block consists of items inside braces. A final expression without ; becomes the block's value; ending that expression with ; discards the value. A block with no final value is invalid in a context that requires a value.

let value = {
    let a = 20;
    let b = 22;
    a + b
}

Calls and braces

A brace after a name can mean a struct literal, a call with block arguments, or a control-flow body. The parser uses the declared kind of the name to tell them apart. A function used as a condition must be called explicitly:

if check() { ... }

The syntax document explains why if check { ... } is parsed differently when check is known to be a function. Calls using parentheses are the unambiguous form.

Operators

  • Logical: &&, ||, ~~, !; keywords and, or, xor, not.
  • Bitwise: :&, :|, :^, :<, :>, <:.
  • Comparison: ==, !=, <, >, <=, >=.
  • Range: .., ..=.
  • Pointer: &value, value^.
  • Cast: value -> type.
  • Assignment: =, +=, -=, *=, /=.

The design intentionally keeps logical and bitwise operators in different symbol families. Plain & is address-of, not bitwise and. The precedence and associativity rules are not fully settled in the v26 document.

Collections

  • Arrays use T[n] and array literals such as [1, 2, 3].
  • Vectors use T<n> and vector literals such as <1, 2, 3>.
  • Tuples use (a, b) and support tuple binding forms.
  • Ranges can be used by for; range slicing is not fully specified for every collection.

Vector indexing is written vector<index>, which depends on the parser knowing the name is a vector. In other contexts, < can mean comparison. Parenthesize comparisons inside an index.

Functions and flags

@Stripped allows a function call to omit parentheses. @Loosely describes functions whose parameter list contains .... Both forms affect how the parser determines argument boundaries. Their complete rules and limitations are in doc/syntax.md.

Open questions

Do not treat items marked Qn in the source specification as settled language behavior. They include default visibility, import binding, multiple-binding semantics, uninitialized values, block return rules, conditional expressions without else, matching and enum patterns, variadic arguments, method receivers, struct declaration equivalence, cast rules, operator precedence, macro substitution, pointer lifetimes and narrowing, heap ownership, nested unions, vector length/capacity, slicing, and numeric-literal defaults.

Compiler architecture

Astry's intended compiler is a direct pipeline. Each stage should own one responsibility, expose the information required by the next stage, and avoid making later stages recover information that an earlier stage already had.

Intended pipeline

source units
    -> lexer
    -> return-type normalization
    -> macro expansion
    -> declaration index
    -> parser / AST
    -> semantic analysis
    -> backend lowering
    -> LLVM IR
    -> object or executable output

The language reference describes the token-based stages before parsing so macro-produced declarations can be indexed before the parser needs to interpret name kinds. The broader design document gives the ownership boundary; the syntax document has the more detailed pipeline.

Source ownership

Source owns a source unit's name and text. Sources owns the ordered set of source units and rejects duplicate names. Source order is supplied by the caller; compilation must not depend on filesystem enumeration order.

The intended ownership flow is:

Source / Sources
    -> tokens
    -> AST / Program
    -> semantic program and resolved symbols/types
    -> backend objects and LLVM context
    -> emitted output

Later stages should consume structured data from earlier stages rather than rereading and reparsing source text. Source text remains available for diagnostics.

The repository also contains src/extra/, including embedded-C and pointer/cast helpers, and src/backend/shortcuts.rs for small backend operations.

Public compiler surface

The library exports Source, Sources, Compiler, CompilerOptions, Target, Output, Error, and several language representation types. A Source contains a name and text. Sources::new rejects duplicate source names. The currently defined target is Target::Native; output variants are Output::Executable and Output::Object.

These options are data structures, not proof that the output pipeline is implemented. compile_with_options validates the options and prepares each parsed semantic program, then returns Error::StageNotImplemented(Stage::Semantic).

Backend boundary

The backend uses ani rather than exposing LLVM's full object model throughout the compiler. The current wrappers include an LLVM context, modules, functions, and instruction handlers. Tests demonstrate construction of simple i32 and void functions and return instructions. Full lowering from a semantically checked Astry program to LLVM IR and native output remains unfinished.

Determinism and errors

Source units and declarations should be processed in stable order. Diagnostics and emitted symbol names should be deterministic. Errors are explicit; the design does not call for silently recovering from an unsupported target or failed stage.

Diagnostics

Astry defines error categories for input, options, target support, lexing, parsing, semantic analysis, and backend lowering. The current formatting is implemented in src/utility/error.rs; the ideal format and the rendered semantic-span format are not fully aligned yet.

Error categories

ErrorMeaning
IoSource file or another input operation failed
InvalidOptionsCompiler input or options are invalid
UnsupportedTargetThe backend does not support the requested target
LexSource text could not be tokenized
ParseTokens do not form valid syntax or structure
SemanticA parsed construct violates language meaning or type rules
BackendA semantic program could not be lowered to the backend
StageNotImplementedCompilation reached a stage that is not implemented

Lexer and parser diagnostics carry a line and column. Semantic diagnostics carry a SourceSpan. with_source attaches the source name to an error.

Current output

The CLI prints an error to standard error and exits with status 1. A source-wrapped lexer/parser diagnostic is currently formatted along these lines:

E [src/main.as][3][8] unexpected token

Semantic errors use a start and end span, for example:

E [src/main.as][3:8-3:12] type mismatch

The exact message depends on the error and source. This is a description of the current implementation, not a finalized user-facing diagnostic specification.

Useful reports

When reporting a compiler issue, include:

  1. The smallest source file that reproduces it.
  2. The command used.
  3. The full diagnostic text.
  4. The expected behavior and the observed behavior.
  5. The repository branch or commit used.

For a lexer or parser issue, include the exact token or syntax that triggered the failure. For a semantic or backend issue, also include the relevant type declarations and surrounding function.

Known gap

doc/syntax.md shows semantic diagnostics using [Line][Column], while the current Error display uses a range such as [start_line:start_column-end_line:end_column]. todo/utility.md tracks this mismatch. The CLI also lacks separate exit codes for usage, source, semantic, backend, and toolchain failures.

Status and roadmap

Astry is under active development. Read the syntax document as the language design, not as a feature-completion matrix.

Current state observed in the repository

AreaState
Rust crate and command-line entry pointPresent; CLI accepts one source-file argument
LexerImplemented with tokenization tests; lexer TODO still lists token conformance and operator cleanup
ParserProgram/declaration parsing and some expression parsing exist; implementation and tests do not establish full v26 conformance
Macro expansion and function-return normalizationImplemented as token-stage helpers used before program parsing
Semantic analysisData structures and type-syntax groundwork exist; the complete validation and resolution stage is unfinished
LLVM wrappersBasic context/module/function/handler wrappers exist; unit tests cover small IR operations

Object/executable outputNot available through the current compile path

The strongest current limitation is explicit in Compiler::compile_with_options: after preparing the semantic program for each source, it returns StageNotImplemented(Stage::Semantic). A valid program therefore cannot currently pass through the CLI to produce native output.

Implementation order

The plan in doc/plan.md organizes the work roughly as follows:

  1. Establish compiler input ownership, error handling, and a small public API.
  2. Finish lexer conformance to the v26 token rules.
  3. Complete the parser and AST for the stable language surface.
  4. Implement semantic analysis: name resolution, scopes, visibility, types, overloads, casts, pointers, and control-flow rules.
  5. Finalize the ani boundary and backend representations.
  6. Lower checked programs into LLVM IR.
  7. Implement runtime and standard-library operations.
  8. Emit object files and executables for supported native targets.
  9. Revisit experimental features after the core language works.

Unresolved specification questions

doc/syntax.md marks unresolved behavior from Q1 through Q20. The major groups are:

  • Declarations and modules: default visibility, nested import binding, multiple-name binding semantics, and uninitialized storage.
  • Blocks and control flow: final-expression return behavior, conditionals without else, match wildcard/exhaustiveness, and enum patterns.
  • Calls and methods: variadic argument typing/boundaries and how into methods receive their receiver.
  • Types and casts: equivalence of struct declaration forms, valid cast pairs, operator precedence/associativity, and numeric-literal default types.
  • Macros: whether substituted arguments are parenthesized and how body braces participate in expansion.
  • Pointers and memory: optional-pointer narrowing, lifetimes of addresses to locals, who frees vector and string storage, and nested union behavior.
  • Collections: vector length versus capacity for uninitialized forms, vector method return types, and range slicing results.

Do not silently invent answers to these questions in code or documentation. Record a decision in doc/syntax.md when the language design resolves one.

Cross-document inconsistencies

The repository contains a few design/status mismatches that should be resolved as implementation proceeds:

  • doc/design.md and doc/plan.md put modules and macros among experimental features, while doc/syntax.md describes module/import handling and macro expansion in its main pipeline.
  • doc/goal.md links to syntaxdesign-26.8.md, but the tracked syntax file is doc/syntax.md.
  • The syntax document's example diagnostic format differs from the current Error display for semantic spans.
  • The lexer and semantic TODOs identify operator/type-token mismatches that need conformance checks.
  • src/semantic/semantic.rs currently spells the internal flag variants Striped and Lossely, while the syntax uses @Stripped and @Loosely; reconcile these names when flag handling is implemented.

The syntax document should remain authoritative for spelling and grammar. Other documents should be updated when a decision changes.

Contributing

Keep changes narrow and keep the implementation, specification, tests, and documentation in agreement.

Before changing syntax

  1. Read the relevant section in doc/syntax.md.
  2. Check whether the behavior is stable or marked with an open question (Q1 through Q20).
  3. If the rule is unresolved, decide and document the rule before depending on it in multiple compiler stages.
  4. Add or update tests for accepted syntax, rejected syntax, and source locations where relevant.
  5. Update the lexer/parser/semantic TODO when the implementation status changes.

Stage boundaries

The compiler is intended to pass structured information forward:

  • The lexer owns tokenization and lexical diagnostics.
  • The parser owns syntactic structure and produces the AST.
  • Semantic analysis resolves names and types and validates language rules.
  • The backend lowers a checked semantic program to LLVM IR.
  • Output handling emits the requested artifact.

Do not compensate for a missing invariant in a later stage by reparsing source text or silently recovering from an earlier-stage failure.

Development commands

cargo build
cargo test

Build requirements include the LLVM/toolchain setup required by ani. A passing unit-test suite is not currently the same as a passing end-to-end compilation test: the compile entry point intentionally stops at the semantic stage while that stage remains unimplemented.

Tests to add

For lexer changes, test tokens and malformed inputs. For parser changes, test both AST shape and rejection cases. For semantic changes, test name resolution, types, overload selection, visibility, and deterministic source spans. For backend changes, verify generated LLVM IR and add end-to-end tests once the frontend-to-backend path exists.

Documentation style

  • Use plain, exact language.
  • Describe actual behavior, not intended behavior, as current behavior.
  • Keep examples small and runnable when the toolchain supports them.
  • State preconditions, failures, and unresolved behavior explicitly.
  • Prefer one sentence per source line in documentation files.
  • Link to the source specification instead of copying the entire grammar into several places.
  • Avoid introducing architectural layers for features the language does not yet require.

Pull requests

Keep each change focused. Explain the behavior changed, the tests run, and any known limitations. If a language rule changes, update the syntax reference and related examples in the same change.
